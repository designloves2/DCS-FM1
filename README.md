# DCS-FM1 System

## 상세 개발 명세서 (Implementation Specification)

- 문서 버전: 0.3.1
- 상태: 공개 자료 조사 + 설계 결정(2026-11) 반영 / 실물 검증 전 개발 기준안
- 개정 요약: 펌웨어 베이스 확정(fm1-base), 전송 방식 확정(USB-MIDI SysEx), Flash 쓰기 범위 축소(백업/복구 도구로 이동), 디스플레이 표시를 v1 범위에 포함
- 대상 시뮬레이터: DCS World
- 대상 기체: F/A-18C Hornet 전용
- 대상 하드웨어: M-VAVE FM-1
- 개발 산출물:
  1. FM-1 Custom Firmware
  2. DCS-FM1 Mapper (Windows)
  3. Firmware–Mapper 공통 통신 프로토콜
  4. 백업/복구 도구 (Flash 쓰기·복구 전담, 별도 수용 기준 §12.5)

> **중요한 개발 원칙**
> 
> 이 문서는 공개 소스 및 기술 문서를 조사한 결과를 반영한 구현 기준안이다. 공개 자료에서 확인된 사실, 커뮤니티 실측/역공학 자료, 아직 실물 검증이 필요한 항목을 구분한다. 사용자가 구입한 FM-1 두 대는 서로 다른 하드웨어 리비전일 수 있으므로 각 장치를 독립적으로 식별한다. DCS 펌웨어 앱은 플래시에 쓰지 않으며, 구형·신형 플래시 조합 지원은 백업/복구 도구의 요구사항이다. 실물 장비가 없는 개발 초기에는 공개 소스, 에뮬레이터, 가상 플래시 이미지 및 PC 측 시뮬레이터로 가능한 작업을 선행한다. 실제 플래시 쓰기/복구는 장치별 사전 백업 및 검증 절차가 마련되기 전까지 금지한다.

# 1. 프로젝트 개요

## 1.1 목적

M-VAVE FM-1을 DCS World F/A-18C의 보조 시스템 패널 컨트롤러로 활용한다.

사용자는 Windows 프로그램인 **DCS-FM1 Mapper**에서 FM-1의 물리 버튼과 노브를 원하는 DCS-BIOS 컨트롤에 자유롭게 할당한다.

Mapper는 DCS-BIOS의 컨트롤 정의 및 상태 데이터를 활용하여 설정 화면을 구성하고, RUN 상태에서는 양방향 통신을 수행한다.

- FM-1 → Mapper: 버튼, 노브 조작 이벤트 전달
- Mapper → DCS-BIOS: 사용자가 설정한 명령 전달
- DCS-BIOS → Mapper: 항공기 상태 데이터 수신
- Mapper → FM-1: 기능명, 현재 상태값, 표시 정보를 전달
- FM-1: 전달받은 정보를 화면에 표시

## 1.2 기존 장비와의 관계

사용자는 이미 실물 UFC와 좌우 DDI를 구축하여 DCS-BIOS로 사용하고 있다.

따라서 FM-1은 기존 UFC/DDI를 대체하지 않는다. 기존 장비에 추가되는 보조 시스템 패널이다.

주요 사용 대상은 다음과 같다.

- ELEC: 전기 계통
- ECS: 환경 제어 계통
- INTR LT: 실내 조명
- SENSOR: 센서 계통
- 기타 F/A-18C의 보조 시스템 및 패널 조작부

실제 지원 컨트롤은 설치된 DCS-BIOS의 F/A-18C 정의를 기준으로 결정한다. 위 그룹명은 Mapper의 사용자 분류 및 프로파일 구성 예시이며, 모든 기능이 DCS-BIOS에서 지원된다고 미리 단정하지 않는다.

## 1.3 핵심 목표

1. FM-1 순정 펌웨어를 보존하고 별도 DCS 펌웨어를 제공한다.
2. 음악용 순정 모드와 DCS 전용 모드를 분리한다.
3. 버튼과 노브의 기능을 펌웨어에 고정하지 않는다.
4. 모든 조작 매핑은 Mapper에서 설정한다.
5. DCS-BIOS 컨트롤 정보를 자동으로 읽어온다.
6. DCS-BIOS 명령과 실제 항공기 상태를 양방향으로 연동한다.
7. FM-1 여러 대를 동시에 연결하고 각각 독립적으로 설정한다.
8. RUN/STOP으로 통신 및 조작 기능을 명확하게 제어한다.
9. FM-1 디스플레이(240×240)에 기능명, DCS 상태값, 연결 상태를 표시한다.
10. 기존 UFC/DDI 및 기존 DCS-BIOS 설치 구성을 변경하거나 대체하지 않는다.
11. FM-1 디스플레이 표시(라벨/값/stale/연결 상태)를 1차 릴리스(v1) 범위에 포함한다.

## 1.4 비목표(초기 버전 제외)

- 다른 DCS 기체 지원
- FM-1을 범용 MIDI 신디사이저로 대체하는 기능
- 기존 UFC/DDI의 기능 대체
- DCS 항공기 내부 로직 변경
- DCS-BIOS가 제공하지 않는 상태값의 임의 추정
- 검증되지 않은 FM-1 하드웨어 기능을 전제로 한 구현
- Mapper가 DCS World 자체를 실행하거나 종료하는 기능

# 2. 전체 시스템 아키텍처

## 2.1 구성요소

### A. FM-1 Custom Firmware

FM-1 하드웨어에서 실행되는 DCS 전용 펌웨어다.

책임:

- 물리 버튼 입력 감지
- 엔코더/노브 입력 감지
- 입력 이벤트를 공통 프로토콜로 전송
- Mapper에서 전달한 화면 데이터 표시
- 장치 식별 및 연결 상태 제공
- 펌웨어 버전 및 프로토콜 버전 보고
- 연결 끊김 및 오류 상태 표시
- 오디오/BLE/WiFi를 링크하지 않음 (DCS 모드에서 무음)
- 플래시에 설정을 저장하지 않음 (설정의 기준은 Mapper)
- Flash JEDEC ID/UID는 진단 목적으로 읽기만 함

펌웨어는 DCS-BIOS를 직접 구현하지 않는다. DCS-BIOS 통신과 컨트롤 매핑은 Windows Mapper가 담당한다.

### B. DCS-FM1 Mapper

Windows에서 실행되는 통합 제어 프로그램이다.

책임:

- FM-1 장치 검색 및 연결
- 여러 FM-1 장치 구분
- DCS-BIOS 설치 및 통신 상태 확인
- DCS-BIOS 컨트롤 정의 읽기
- 컨트롤 검색 및 필터링
- 버튼/노브 매핑 편집
- 매핑 프로파일 저장 및 불러오기
- MIDI/USB 이벤트 수신
- DCS-BIOS 명령 송신
- DCS-BIOS 상태 데이터 수신 및 해석
- 각 FM-1 디스플레이에 표시할 정보 전달
- RUN/STOP 및 오류 관리

### C. DCS-BIOS

DCS World와 Mapper 사이에서 항공기 컨트롤 및 상태 정보를 교환하는 계층이다.

중요:

- DCS-BIOS는 DCS World 내부의 Export.lua 및 관련 구성요소와 연동된다.
- Mapper는 설치된 DCS-BIOS의 실제 통신 인터페이스와 프로토콜을 확인해 연결해야 한다.
- DCS-BIOS를 새로 설치하거나 기존 구성을 무단 변경하지 않는다.
- Mapper가 DCS-BIOS 런타임을 직접 시작해야 하는지는 설치 구조와 실행 방식 조사 후 결정한다. 기본 동작은 기존 DCS-BIOS가 실행 중인지 확인하고 통신하는 것이다.

### D. 백업/복구 도구

순정 펌웨어 백업, Flash 읽기/쓰기/검증, 복구를 전담하는 PC 측 도구다. 펌웨어 앱과 Mapper와 분리해 배포한다.

책임:

- 장치별 전체 플래시 백업 및 해시 기록
- JEDEC ID/용량 확인 후 허용된 칩에만 쓰기
- 쓰기 후 읽기 검증 및 재부팅 영속성 확인
- ROM 다운로드 모드 진입/복구 절차 수행
- 알 수 없는 Flash ID는 읽기 전용으로 제한

Flash 쓰기 요구는 §3.2와 §12.5에 정의하며, 펌웨어 앱과 Mapper는 이 도구 없이도 정상 동작해야 한다.

## 2.3 모듈 분리 원칙

Mapper 내부는 다음 모듈로 분리한다.

| 모듈  | 책임  |
| --- | --- |
| DeviceManager | FM-1 검색, 연결, 해제, 식별 |
| TransportAdapter | USB/MIDI/Serial 등 실제 연결 방식 추상화 |
| FirmwareProtocol | 펌웨어와의 메시지 인코딩/디코딩 |
| MappingEngine | 물리 입력을 DCS-BIOS 명령으로 변환 |
| DcsBiosCatalog | 컨트롤 정의 및 메타데이터 로드 |
| DcsBiosTransport | DCS-BIOS 데이터 송수신 |
| DcsBiosStateDecoder | 상태 데이터 해석 |
| DisplayManager | 장치별 화면 표시 데이터 생성 |
| ProfileManager | 매핑 프로파일 저장/로드 |
| RunController | RUN/STOP 및 전체 상태 관리 |
| Diagnostics | 로그, 오류, 통신 진단 |

UI와 장치 통신 로직을 분리한다. UI가 멈추더라도 통신 스레드가 안전하게 종료될 수 있어야 한다.

### 공식 펌웨어 및 빌드 환경

FM1 Open 공식 저장소의 현재 공개 README는 V14를 기준으로 설명한다. README에 명시된 빌드 조건은 다음과 같다.

- Windows x64
- PowerShell, `curl.exe`, `tar.exe`
- JieLi Windows Toolchain 2.5.3
- PI32v2 clang 4.0.1
- `FM1_PI32_TOOLCHAIN` 환경변수를 툴체인의 `pi32` 폴더로 지정
- CPU target `r3`
- 로컬 펌웨어 빌드 예시: `./sdk/Build.ps1 -FirmwareOnly -Toolchain 'C:\JL\pi32'`

소스와 SDK는 같은 릴리스에 해당하는 묶음을 사용한다. README는 2.5.2용으로 고정된 구형 V14 키트가 2.5.3 툴체인을 거부할 수 있다고 경고한다. SDK manifest 검사 기능을 임의로 끄지 않는다.

FM1 Open은 순정 V15로 돌아가는 Workbench 경로 및 표준 업데이트 프로토콜을 안내하지만, 모든 커스텀 펌웨어/하드웨어 리비전에 대한 무조건적인 복구 보증은 아니다. 펌웨어 패키지와 프로젝트/샘플 데이터의 포맷 호환성도 별개다.

### 개발 베이스에 대한 결정

1. 기준 베이스는 **fm1-base(MPL-2.0)와 felucca-bsp(MPL-2.0)** 로 확정한다. 커밋 SHA를 고정하고 업그레이드는 별도 브랜치에서만 수행한다. fm1-base는 화면·폰트·패널·엔코더·LED·USB-MIDI 양방향·저장·업데이트와 함께 PC 호스트 시뮬레이터 및 브라우저 에뮬레이터를 제공한다.
2. 공식 FM1 Open V14는 하드웨어 사실, 플래시 레이아웃, 패키지/업데이트 포맷, 보드 헤더(`fm1_lcd_hw.h`, `fm1_input.h`)의 참고 자료로 사용한다. 그 응용 구조(신디사이저 UI, 바이너리 사운드 엔진)는 채택하지 않는다.
3. m-bootloader는 복구·플래시 프로토콜의 참고 구현으로만 분석한다. 사용자 장치의 부트로더를 교체하지 않는다. 순정 부트로더에서도 SysEx soft-key(`F0 22 24 35 7D F7`)로 ROM 다운로드 모드에 진입해 백업할 수 있다.
4. DCS 펌웨어는 오디오, BLE, WiFi를 링크하지 않는다. 따라서 JieLi Bluetooth/WiFi 바이너리 라이브러리와 그 재링크 조건을 요구하지 않는다.
5. 예산 기준: 앱 슬롯 581KB, RAM 96KB(`.data`/`.bss`) + 336KB 풀. 무선이 없는 fm1-base 템플릿은 77KB/27KB로 측정되었다. 화면·프로토콜·폰트가 이 예산을 넘지 않도록 관리한다.

## 3.2 순정 펌웨어 보존 및 복구

공개 자료 조사 결과, FM-1은 JieLi ROM 다운로드 모드와 USB 기반 업데이트/복구 경로가 존재한다. 공개 m-bootloader 프로젝트는 FM-1에서 키 조합으로 ROM 다운로드 모드 진입, USB MIDI 기반 재설치, 플래시 백업, 복구 메뉴를 구현했다고 설명한다.

중요한 제한:

- m-bootloader는 공식 제조사 부트로더가 아닌 MIT 라이선스의 커뮤니티 구현이다.
- 신형 UCUN 플래시에서의 동작은 프로젝트 README에 제한적 테스트 및 위험 경고가 명시되어 있다.
- 펌웨어/부트 영역/키 영역/사용자 데이터가 단일 플래시 안에 존재할 수 있으므로 단순히 앱 영역만 백업했다고 전체 복구가 보장되지 않는다.
- 공식 FM1 Open의 V15 복귀 지원(현행 배포는 V16 기준)과 커뮤니티 부트로더의 복구 방식은 서로 다른 경로다. 하나를 다른 하나와 동일하게 취급하지 않는다.

순정 장치 백업 경로(부트로더 교체 없이):

- 순정 펌웨어는 SysEx soft-key(`F0 22 24 35 7D F7`)로 칩의 ROM USB 다운로드 모드에 진입한다. M-Flasher가 이 메시지를 전송한다.
- 다운로드 모드에서 전체 플래시(부트/키/사용자 영역 포함)를 읽어 백업할 수 있다. 따라서 m-bootloader 설치가 백업의 전제조건이 아니다.
- m-bootloader는 백업 이후의 선택 사항이며, 신형 UCUN 플래시에서는 실기 리스크가 보고되어 있으므로 v1 기본 절차에서 제외한다.

필수 요구사항:

- 두 FM-1 각각에 대해 플래시 ID, 전체 플래시 읽기 가능 여부, 백업 파일 해시를 별도로 기록한다.
- 각 장치의 원본 전체 플래시 이미지 및 가능한 경우 사용자 데이터 영역을 별도 백업한다.
- 백업은 장치 A/B를 섞지 않고 일련번호/USB 경로/파일 해시와 연결한다.
- 복구 가능한 ROM 다운로드 경로와 실제 복구 절차를 소스/문서 수준에서 먼저 분석한다.
- 백업 및 복구 경로가 장치별로 검증되기 전에는 커스텀 펌웨어를 실제 장치에 기록하지 않는다.
- 플래시 쓰기 전후 전체 이미지/영역 해시 및 CRC를 비교한다.
- 전원 차단, USB 연결 해제, 업데이트 중단 시나리오를 시뮬레이터에서 먼저 테스트한다.

수용 기준:

- FM-1 #1과 #2 각각에 대해 독립된 원본 백업을 확보한다.
- 복구 모드 진입 방법과 공식/커뮤니티 도구의 적용 범위를 문서화한다.
- 실물 장치 복구 테스트가 성공하기 전까지는 '복구 검증 완료'로 표시하지 않는다.

### 백업/복구 도구의 Flash 지원 요구 (펌웨어 앱 범위 제외)

DCS 펌웨어는 플래시에 설정을 쓰지 않는다. 아래 요구는 PC 측 백업/복구/플래시 도구에 적용한다.

- `FlashDevice` 공통 인터페이스와 칩별 프로파일/드라이버를 분리한다.
- 공통 인터페이스: `read_jedec_id`, `read`, `write`, `erase_sector`, `erase_block`, `wait_ready`, `read_status`, `verify`.
- 알려진 ID `0x856014`, `0xB36014`만 명시적으로 허용한다.
- 알 수 없는 ID는 읽기 전용 진단만 허용하고 쓰기/삭제/OTA를 차단한다.
- 칩별 데이터시트 또는 소스에서 확인되지 않은 명령/타이밍/상태 비트는 추측하지 않는다.
- 쓰기 전에 ID와 용량을 다시 확인하고, 쓰기 후 읽기 검증 및 재부팅 후 영속성 검증을 수행한다.
- Flash ID 검사 지점(앱 저장, 업데이트 로더, 복구 진입, 플래시 도구)의 결과를 일관되게 관리한다.
- 도구는 장치를 Flash ID가 아니라 장치별 세션(Flash UID/USB 경로)으로 구분한다.

# 4. FM-1 Custom Firmware 요구사항

## 4.0 하드웨어 리비전 및 Flash 호환성 (백업/복구 도구 범위)

DCS 펌웨어 애플리케이션은 플래시에 설정을 쓰지 않으며, JEDEC ID/UID를 진단 목적으로 읽기만 한다. 따라서 이 절의 쓰기·삭제·영속성 요구는 §3.2의 "백업/복구 도구의 Flash 지원 요구"에 적용하며, 펌웨어 앱의 수용 기준에는 포함하지 않는다. 앱에서 Flash ID를 읽지 못하더라도 입력/화면/프로토콜 기능은 정상 동작해야 한다.

사용자가 보유한 FM-1 두 대는 서로 다른 생산 리비전일 수 있다. 두 장치가 같은 외형/모델명이라는 이유로 동일한 플래시 칩이라고 가정하지 않는다.

현재 공개 커뮤니티 자료에서 확인되는 1MiB SPI NOR 플래시 변형은 다음과 같다.

| 변형  | 부품 표기 | JEDEC ID | 상태  |
| --- | --- | --- | --- |
| 구형  | Puya P25Q80H 계열 | `0x856014` | 다수 기존 펌웨어의 기준 칩 |
| 신형  | UCUN UC25HQ80 | `0xB36014` | 2026년 하반기 일부 생산분에서 보고 |

두 ID는 커뮤니티 개발 자료 및 플래셔 코드에서 확인되는 값이다. 제조사 공식 BOM/회로도가 공개된 것으로 간주하지 않는다. 두 칩은 1MiB SPI NOR로 보고되며 기존 SPI NOR 명령/레이아웃을 공유한다는 커뮤니티 소스가 있지만, 모든 전기적 타이밍/상태 레지스터가 완전히 동일하다고 가정해서는 안 된다.

### 반드시 지원할 장치 조합

| FM-1 #1 | FM-1 #2 | 지원  |
| --- | --- | --- |
| Puya 구형 | Puya 구형 | 필수  |
| Puya 구형 | UCUN 신형 | 필수  |
| UCUN 신형 | Puya 구형 | 필수  |
| UCUN 신형 | UCUN 신형 | 필수  |

위 "필수"의 의미는 두 가지다. 펌웨어 앱은 네 조합 모두에서 동일하게 동작해야 하고(쓰기 없음, ID는 진단용), 쓰기·백업·복구는 백업/복구 도구가 네 조합 모두를 지원해야 한다.

장치별 독립 식별:

1. 각 FM-1의 초기 부팅/진단 시 Flash JEDEC ID를 개별적으로 읽는다.
2. Mapper에 장치별 `flash_vendor`, `flash_model`, `flash_jedec_id`, `flash_capacity`, `hardware_revision` 정보를 진단/표시용으로 보고한다.
3. 장치 A의 Flash ID를 장치 B에 재사용하거나 전역 단일 값으로 캐시하지 않는다.
4. 장치 재연결 시 해당 장치의 정보를 다시 확인한다.
5. Flash ID를 읽을 수 없는 경우 임의로 구형으로 간주하지 않고 `UNKNOWN`으로 처리한다.

### Flash 드라이버 설계

칩 프로파일 분리, 허용 ID 제한, 쓰기 검증 등 드라이버 요구사항은 §3.2 "백업/복구 도구의 Flash 지원 요구"로 이동했다. 펌웨어 앱은 이 드라이버를 링크하지 않는다.

### 공개 소스에서 확인할 주요 코드 위치

m-bootloader 저장소는 다음 구현을 포함한다.

- Stage 0 / Stage 1 부팅 및 복구 메뉴
- USB MIDI 업데이트 프로토콜
- ROM 다운로드 모드용 flash loader
- 플래시 읽기/쓰기 도구 연동
- 시뮬레이션 기반 부팅/메뉴/로더 테스트
- 실제 장치 이미지 및 M-VAVE 패키지를 사용하는 일부 선택 테스트

코딩 에이전트는 이 저장소에서 JEDEC ID 검사, 플래시 명령, 영역 레이아웃, 패키지 검증, 업데이트 상태 전이를 추적하고, 해당 코드가 FM1 Open의 플래시 드라이버와 어떻게 다른지 비교 보고한다. 코드 복사 전 MIT/GPL 등 각 파일의 라이선스를 확인한다.

## 4.1 펌웨어 모드

다음 두 모드를 구분한다.

- STOCK: 제조사 순정 펌웨어
- DCS: DCS-FM1 전용 펌웨어

전환은 부팅 메뉴가 아니라 **펌웨어 재플래시**로 수행한다(업데이트 프로토콜 또는 M-Flasher). 부팅 시 모드 선택 메뉴는 지원하지 않는다. 두 모드의 프로젝트/프리셋/샘플 포맷은 상호 호환되지 않으므로, 전환 전 백업을 요구하고 사용자에게 명시한다.

## 4.2 입력 처리

### 버튼

각 버튼은 다음 이벤트를 생성할 수 있어야 한다.

- pressed
- released
- long_pressed (하드웨어/펌웨어에서 안정적으로 감지 가능한 경우)
- repeated (반복 입력이 필요한 경우, 선택 사항)

버튼의 의미는 펌웨어에 고정하지 않는다. 물리 입력 ID만 Mapper에 전달한다.

### 엔코더/노브

각 엔코더는 다음 정보를 전달한다.

- encoder_id
- direction: clockwise / counterclockwise
- delta: 회전 변화량
- timestamp 또는 순서 번호

엔코더 푸시 스위치의 유무는 공개 자료로 확인되지 않았다. 확인 전까지는 엔코더 전용 입력으로 설계하고, 푸시가 확인되면 별도 버튼 ID로 승격한다.

엔코더를 버튼처럼 처리하지 않는다. Mapper가 해당 입력을 INC/DEC 또는 기타 동작으로 해석한다.

### 아날로그 노브 여부

FM-1의 노브가 물리 엔코더인지 절대 위치형 포텐셔미터인지 확인한다. 실제 하드웨어 특성에 따라 입력 데이터 모델을 결정한다.

## 4.3 화면 출력

Mapper가 화면 출력 기능을 제공하는 경우 다음 항목을 표시한다.

- 장치 별칭 또는 번호
- 현재 선택된 기능 그룹
- 현재 컨트롤 이름/짧은 라벨
- 현재 DCS-BIOS 값
- 값의 단위 또는 표시 형식
- 통신 상태
- 오류 상태

화면 사양과 표시 규칙:

- 240×240, RGB565, ST7789 계열. 텍스트는 장치에서 렌더링하고 Mapper는 문자열만 전송한다.
- 라벨 영역과 값 영역을 분리하고, 값 변경 시 값 영역만 다시 그린다.
- 표시 문자열은 길이 제한(라벨 16자, 값 8자 기준)을 두고 초과분은 말줄임 처리한다.
- 화면 갱신은 변경 시에만 수행하며, 입력 이벤트 처리보다 낮은 우선순위를 둔다.
- 백라이트는 소등할 수 없으므로(§3.3) 야간 모드는 검은 화면으로 대체한다.

## 4.4 장치 연결 상태

펌웨어는 Mapper에 다음 정보를 보고해야 한다.

- firmware_version
- protocol_version
- device_id (하드웨어 고유 ID가 확인된 경우)
- device_model
- hardware_revision (확인 가능한 경우)
- flash_vendor / flash_model / flash_jedec_id / flash_capacity
- flash_uid (조회 가능한 경우, 다중 장치 세션 식별자)
- flash_support_status: supported / read_only_unknown / error
- usb_port_name (Mapper가 관측한 포트 이름)
- input_count
- display_capabilities
- audio_capabilities (해당 없음: DCS 펌웨어는 오디오를 링크하지 않음)

고유 ID를 얻을 수 없다면 Mapper에서 포트 경로, USB serial number 등 사용 가능한 식별자를 조합한다. 동일 모델 2대는 Windows에서 같은 포트 이름(`FM-1 MIDI 1`)으로 열거되므로, 포트 이름/인덱스만으로 장치를 확정하지 않고 HELLO의 `flash_uid`로 세션을 고정한다.

## 5.3 DCS-BIOS 컨트롤 카탈로그

Mapper는 설치된 DCS-BIOS의 실제 컨트롤 정의를 읽어야 한다.

요구사항:

- 설치 경로 검색
- 사용자가 경로를 직접 지정할 수 있는 기능
- 컨트롤 정의 파일 로드
- JSON 파싱 오류 표시
- 컨트롤 이름 검색
- 설명 검색
- 명령 지원 여부 표시
- 상태 출력 지원 여부 표시
- 명령 형식 및 허용값 표시
- 컨트롤별 원본 정의 확인 기능
- `doc/json`이 없거나 버전이 다르면 `control-reference.html` 또는 모듈 Lua 정의로 폴백

컨트롤 카탈로그는 DCS-BIOS 버전/기체 모듈 버전과 함께 캐시한다. 정의 파일이 변경되면 다시 읽는다.

참고: `doc/json`은 DCS-BIOS 저장소에 포함된 정적 파일이 아니라 **설치 시 생성되는 산출물**이다. 사용자 설치본에 따라 존재하지 않을 수 있으므로, 경로 탐색 실패를 정상 상태로 처리하고 폴백 경로를 제공한다.

중요:

- 컨트롤 이름과 명령 이름을 임의로 만들어내지 않는다.
- 설치된 F/A-18C 정의에 실제 존재하는 항목만 사용자에게 제공한다.
- 입력 명령이 없는 상태 출력 전용 컨트롤은 출력 전용으로 표시한다.
- 상태 출력이 없는 명령 전용 컨트롤은 상태 표시를 지원하지 않는다고 표시한다.

## 5.4 매핑 편집

사용자는 물리 입력을 선택한 뒤 DCS-BIOS 컨트롤을 선택해 할당한다.

지원해야 할 동작 유형:

| 동작  | 설명  | 적용 조건 |
| --- | --- | --- |
| INC | 값 증가 | 해당 명령이 증가 동작을 지원할 때 |
| DEC | 값 감소 | 해당 명령이 감소 동작을 지원할 때 |
| TOGGLE | 상태 전환 | 토글 동작 또는 적절한 명령이 존재할 때 |
| SET | 지정값 설정 | 명령이 값 설정을 지원할 때 |
| PRESS/RELEASE | 누름/해제 | momentary 명령에 적합할 때 |
| CYCLE | 여러 값 순환 | 허용값 및 순환 규칙을 명시할 수 있을 때 |

각 동작은 선택한 DCS-BIOS 컨트롤의 실제 명령 형식에 맞게 제한한다. 모든 컨트롤에 모든 동작을 허용하지 않는다.

# 6. DCS-BIOS 통신 및 상태 데이터

## 6.1 통신 방식 확인

구현 전 현재 설치된 DCS-BIOS 버전의 공식 문서와 소스 코드를 확인한다.

확인 대상:

- 명령 송신 방식
- 상태 데이터 수신 방식
- UDP 포트 및 방향
- 패킷/문자열 형식
- 명령 종결 문자
- 상태 데이터 주소/바이트 표현
- Sync 및 방 단위 처리
- Export.lua 연동 방식
- 설치 버전별 차이

기존 MidiCCMapper의 DCS-BIOS 출력 코드를 먼저 검토한다. 현재 구현은 UDP 7778 송신만 제공하며 상태 수신/디코더는 없다. 송신·카탈로그 로더·LEARN 자산은 재사용하고, 수신/디코더는 신규 모듈로 추가한다. 이미 작동하는 부분을 불필요하게 재작성하지 않는다.

## 6.2 상태 데이터 수신

Mapper는 DCS-BIOS에서 상태 데이터를 받아 다음을 수행한다.

1. 데이터 수신
2. 프로토콜 프레이밍 및 동기화 처리
3. 상태 주소/값 디코딩
4. 해당 컨트롤 정의와 연결
5. 현재 상태 캐시 갱신
6. 매핑된 FM-1 화면에 업데이트 전송

상태값을 수신하지 못한 경우 마지막 값을 실제 현재값처럼 표시하지 않는다. stale 상태임을 표시하거나 값 표시를 비활성화한다.

## 6.3 명령 송신

명령은 DCS-BIOS 컨트롤 정의에 기록된 실제 명령 형식에 맞춰 생성한다.

주의:

- 명령 문자열을 추측해서 만들지 않는다.
- SET 값의 허용 범위를 검증한다.
- INC/DEC는 정의된 step 또는 프로토콜 규칙을 사용한다.
- 명령 송신 실패를 성공으로 표시하지 않는다.
- 버튼 입력이 짧은 시간에 반복될 경우 과도한 명령 송신을 방지한다.

## 6.4 RUN 상태

RUN을 누르면 다음 순서로 동작한다.

1. 현재 프로파일 유효성 검사
2. FM-1 장치 연결 상태 확인
3. 펌웨어/프로토콜 호환성 확인
4. DCS-BIOS 설치 및 통신 설정 확인
5. DCS-BIOS 통신 수신기 시작
6. DCS-BIOS 명령 송신기 준비
7. 상태 데이터 동기화 대기
8. FM-1 화면 초기화 데이터 전송
9. 입력 이벤트 처리 활성화
10. RUN 상태 표시

DCS-BIOS 상태 동기화가 완료되기 전에는 실제 입력 명령을 보내지 않는 안전한 초기화 정책을 기본으로 한다. 단, 사용자가 별도로 허용하는 옵션을 만들 경우 경고 및 명확한 상태 표시가 필요하다.

## 6.5 STOP 상태

STOP을 누르면:

- 새로운 입력 명령 송신 중단
- 입력 이벤트 처리 중단
- DCS-BIOS 수신 스레드 정상 종료
- 장치 화면에 STOP 또는 연결 대기 표시
- 장치 연결 자체는 유지할지 여부를 설정으로 선택 가능
- 로그 기록 유지

STOP은 펌웨어를 종료하거나 FM-1을 재부팅하는 동작이 아니다.

# 7. FM-1 ↔ Mapper 공통 통신 프로토콜

## 7.1 기본 원칙

펌웨어와 Mapper는 DCS-BIOS 프로토콜을 직접 공유하지 않는다. 양쪽 사이에 별도의 버전 관리 가능한 장치 프로토콜을 정의한다.

USB-MIDI(class-compliant)를 기본 전송 방식으로 확정한다. SysEx 프레임을 사용하고, JSON 문자열은 장치와 주고받지 않는다(JSON은 PC 측 프로파일 저장에만 사용).

프레임:

```
F0 7D 44 43 53 <type> <len_lo> <len_hi> <payload…> <crc8> F7
```

- `7D`는 비상업/교육용 SysEx ID다. fm1-base 화면 리더 등 다른 FM-1 SysEx와 구분하기 위해 서브ID `44 43 53`("DCS")을 둔다.
- `type` 1바이트, `len`은 payload 길이(little-endian, 최대 512), `crc8`은 type/len/payload 전체에 대한 CRC-8.
- USB Serial/CDC 또는 HID는 USB-MIDI로 요구 성능을 낼 수 없음이 확인될 때만 폴백으로 검토한다. 폴백 시에도 프레임 구조는 유지한다.

## 7.2 프로토콜 요구사항

- protocol_version 포함
- message_type 포함
- device_id 또는 연결 세션 ID 포함
- 메시지 길이 검증
- 잘못된 메시지 무시 및 오류 로그
- 화면 업데이트와 입력 이벤트의 우선순위 분리
- 연결 유지 및 재연결 처리
- 펌웨어와 Mapper 버전 호환성 확인
- 바이너리 인코딩 사용 (JSON 문자열 전송 금지)
- 프레임 CRC8 검증, 불일치 시 폐기 및 카운터 증가
- 입력 이벤트는 `sequence`로 순서 보존, DISPLAY는 최신값 우선
- 512바이트 초과 메시지는 분할하지 않고 폐기

## 7.3 논리 메시지 타입

다음은 논리적 메시지 정의다. 인코딩은 §7.1의 바이너리 프레임을 사용한다.

| 메시지 | 방향  | 목적  |
| --- | --- | --- |
| HELLO | Device → Mapper | 장치 최초 등록 |
| HELLO_ACK | Mapper → Device | 등록 승인 |
| GET_CAPABILITIES | Mapper → Device | 기능 조회 |
| CAPABILITIES | Device → Mapper | 버튼/노브/화면 정보 |
| INPUT_EVENT | Device → Mapper | 버튼/노브 입력 |
| DISPLAY_UPDATE | Mapper → Device | 화면 갱신 |
| DISPLAY_BULK | Mapper → Device | 페이지 라벨 테이블 일괄 갱신 |
| HEARTBEAT | 양방향 | 연결 유지 |
| STATUS | 양방향 | 상태/오류 보고 |
| PING/PONG | 양방향 | 지연 및 연결 확인 |
| GOODBYE | 양방향 | 정상 연결 종료 |

## 7.4 바이너리 메시지 정의

프레임은 §7.1을 따른다. `payload` 필드는 아래와 같다.

| type | 메시지 | 방향  | payload |
| --- | --- | --- | --- |
| `0x01` | HELLO | Device → Mapper | proto_major, proto_minor, fw_major, fw_minor, model_id, hw_rev, input_count, display_flags, flash_uid[8] |
| `0x02` | HELLO_ACK | Mapper → Device | session_id, result(0=accept), reason |
| `0x03` | GET_CAPABILITIES | Mapper → Device | 없음  |
| `0x04` | CAPABILITIES | Device → Mapper | 입력 목록(각 2바이트: id, kind), 디스플레이 능력 |
| `0x10` | INPUT_EVENT | Device → Mapper | input_id, kind, value, sequence(u16) |
| `0x20` | DISPLAY_UPDATE | Mapper → Device | page, flags, label_len, label[], value_len, value[], unit_len, unit[] |
| `0x21` | DISPLAY_BULK | Mapper → Device | page_count, 라벨/단위 테이블 |
| `0x30` | HEARTBEAT | 양방향 | uptime_ms(u32), last_seq(u16) |
| `0x40` | STATUS | 양방향 | error_code, overflow_count(u16) |
| `0x50` | PING / PONG | 양방향 | nonce(u32) |
| `0x60` | GOODBYE | 양방향 | reason |

예시 — 엔코더 1스텝(시계 방향). payload 5바이트, CRC8은 생략 표기:

```
F0 7D 44 43 53 10 05 00  03 01 01 0C 04  <crc8> F7
```

예시 — 화면 갱신(라벨 "INST LIGHT", 값 "65", 단위 "%"). payload 18바이트:

```
F0 7D 44 43 53 20 12 00  00 00 0A 49 4E 53 54 20 4C 49 47 48 54 02 36 35 01 25  <crc8> F7
```

JSON은 프로파일/설정 저장 형식으로만 사용하며 장치 전송에는 쓰지 않는다.

## 7.5 화면 갱신 정책

- 값이 변경된 경우에만 갱신하는 것을 기본으로 한다.
- 너무 잦은 화면 갱신으로 입력 처리 지연이 발생하지 않도록 한다.
- 화면 갱신은 최신 값 우선으로 처리할 수 있다.
- 버튼/엔코더 입력 이벤트는 순서가 보존되어야 한다.
- 화면 데이터가 오래되었으면 stale 상태를 표시한다.

# 10. 안정성 및 예외 처리

## 10.1 장치 연결 해제

RUN 중 FM-1이 분리되면:

- 해당 장치의 입력 처리를 즉시 중단한다.
- 다른 FM-1 장치의 동작은 유지한다.
- 장치 상태를 disconnected로 변경한다.
- 로그에 장치명과 시각을 기록한다.
- 재연결 시 프로토콜 핸드셰이크를 다시 수행한다.

## 10.2 DCS-BIOS 연결 해제

DCS-BIOS 통신이 끊기면:

- 신규 명령 전송 중단
- 상태값을 최신값으로 표시하지 않음
- FM-1 화면에 연결 끊김 표시
- 재연결 시 상태 동기화 후 RUN 복귀 여부 결정

기본값은 자동 재연결 후 상태 동기화가 완료되면 재개하는 방식으로 설계하되, 안전한 명령 상태를 보장할 수 없는 경우 사용자 확인을 요구한다.

## 10.3 잘못된 값

- 허용 범위를 벗어난 SET 값은 송신하지 않는다.
- 정의에 없는 명령은 송신하지 않는다.
- 컨트롤 정의 버전이 달라져 매핑이 무효화되면 경고한다.
- 상태 데이터가 유효하지 않으면 화면에 오류/미확인 상태를 표시한다.

## 10.4 로그

로그에는 다음 정보를 기록한다.

- 시각
- 장치 ID 및 별칭
- 물리 입력 ID
- 매핑 ID
- DCS-BIOS 컨트롤 ID
- 명령 유형
- 송신 결과
- 상태 데이터 변경
- 연결/해제 이벤트
- 예외 및 오류

로그에 불필요한 대량 상태 패킷을 무제한 저장하지 않는다. 파일 크기 제한 및 로그 회전 기능을 제공한다.

- Puya/UCUN/UNKNOWN 조합의 쓰기 차단 검증은 §12.5(백업/복구 도구)로 분리

## 12.5 백업/복구 도구 테스트

Flash 쓰기·복구는 펌웨어 앱의 수용 기준이 아니라 백업/복구 도구의 수용 기준이다.

| ID  | 테스트 | 통과 기준 |
| --- | --- | --- |
| BAK-001 | 장치 백업 | 2대 각각 전체 플래시 읽기 및 해시 일치 |
| BAK-002 | 혼합 리비전 | Puya/UCUN 혼합 구성에서 장치별 독립 동작 |
| BAK-003 | unknown 차단 | `UNKNOWN` ID에서 쓰기/삭제 차단 |
| BAK-004 | 복구 리허설 | 검증된 절차로 순정 이미지 복원 |
| BAK-005 | 영속성 | 쓰기 후 재부팅해도 데이터 유지 |

SIM-FLASH 조합 테스트(§18.5)는 실제 장치 검증 전 단계로 이 표에 준해 수행한다.

# 13. 보안 및 안전 설계

- Mapper는 관리자 권한을 기본 요구하지 않는다.
- 네트워크 통신은 기본적으로 로컬 호스트에서만 수행한다.
- 외부 네트워크로 DCS 상태 데이터를 전송하지 않는다.
- 프로파일은 로드 전에 스키마 및 값 검증을 수행한다.
- 잘못된 패킷은 무시하고 로그에 남긴다.
- 장치 입력 폭주가 발생하면 입력 제한을 적용한다.
- DCS-BIOS 연결 상태가 불명확하면 명령 송신을 중단한다.
- 펌웨어 업데이트 중 전원 차단 위험을 사용자에게 알린다.

# 14. 코딩 에이전트 작업 지침

이 프로젝트는 Claude Sonnet 5.5 또는 DeepSeek 4.1 Flash와 같은 코딩 전용 에이전트가 구현한다.

## 14.1 작업 전 필수 확인

1. 사용자가 제공한 최신 저장소/파일을 기준으로 한다.
2. 기존 MidiCCMapper를 확장하는 경우 현재 소스를 먼저 전체적으로 확인한다.
3. 기존 기능, 기본값, UI 및 설정 파일 형식을 조사한다.
4. 수정 대상 파일과 변경 이유를 먼저 정리한다.
5. 과거 ZIP이나 다른 대화의 파일을 임의로 가져오지 않는다.
6. fm1-base/felucca-bsp의 고정 커밋과 라이선스, 그리고 FM1 Open의 현재 버전/사용 조건을 확인한다.
7. DCS-BIOS 공식 문서 및 실제 설치된 정의 파일을 확인한다.

## 14.2 구현 원칙

- 확인되지 않은 하드웨어 기능을 임의로 구현하지 않는다.
- DCS-BIOS 컨트롤 이름/명령을 추측하지 않는다.
- 실제 정의 파일을 데이터의 기준으로 사용한다.
- 기존 동작하는 코드를 불필요하게 재작성하지 않는다.
- 변경 범위를 작게 나누고 단계마다 빌드/테스트한다.
- 펌웨어와 Mapper의 프로토콜 버전을 일치시킨다.
- 예외를 삼키지 말고 로그로 남긴다.
- UI 스레드에서 블로킹 통신을 수행하지 않는다.
- 장치 연결/해제와 앱 종료 시 리소스를 정상 정리한다.

## 14.3 기존 MidiCCMapper 확장 지침

기존 저장소를 기반으로 할 경우:

- DCS-BIOS 출력 기능을 먼저 검토한다.
- MIDI 입력 리스너의 다중 장치 지원 여부를 확인한다.
- 기존 `inc_dec` 처리의 엔코더 래핑 및 상대값 처리 정확성을 테스트한다.
- DCS-BIOS 상태 수신 기능이 없으면 별도 모듈로 추가한다.
- 장치별 별칭과 고유 ID 관리 방식을 보강한다.
- 기존 키보드/vJoy 기능은 사용자 요청 없이 삭제하지 않는다.
- 기존 프로파일과 설정의 호환성을 유지한다.

## 14.5 토큰/세션 효율 규칙

에이전트 구현 비용의 대부분은 재작업과 불필요한 전체 파일 읽기에서 발생한다. 다음을 강제한다.

1. **계약 우선 동결**: P0에서 `PROTOCOL_SPEC.md`(§7)와 화면 레이아웃(§4.3)을 확정한다. P1~P3는 확정본만 참조하고, 계약 변경은 별도 ADR로만 수행한다. 계약이 흔들리면 펌웨어와 Mapper를 반복 수정해 2~3배 토큰이 소모된다.
2. **부분 읽기 원칙**: fm1-base/felucca-bsp/FM1 Open 벤더 코드를 통째로 읽지 않는다. grep/심볼 검색으로 함수·헤더 단위만 확인하고, 수정 대상 파일만 전문을 읽는다. 벤더 트리 전체 열람은 그 자체로 수십만 토큰을 소모한다.
3. **에뮬레이터 게이트 유지**: P2 하네스를 P3/P5보다 먼저 완성한다. 화면/입력/프로토콜은 에뮬레이터에서 검증하고, 실기 왕복은 P4 게이트로 제한한다. 실기 디버깅은 사람 개입이 많아 토큰 대비 진척이 가장 나쁘다.
4. **테스트 우선**: §12의 BAK/FW/MAP/BIOS 케이스를 구현 전에 테스트로 작성한다. 실패 테스트 → 구현 → 통과 순서로 진행해 재작업 루프를 줄인다.

# 16. 최종 제품 정의

최종 제품은 세 개의 독립 실행/배포 구성요소(Firmware, Mapper, 백업/복구 도구)와 하나의 공통 프로토콜로 구성한다. FM-1 두 대가 서로 다른 Flash 리비전이어도 앱은 Flash 쓰기를 하지 않으므로 동일하게 동작해야 하며, 백업/복구 도구는 장치별 Flash 프로파일을 분리해 지원한다.

## A. FM-1 Custom Firmware

FM-1을 DCS 전용 입력/표시 장치로 동작시킨다.

## B. DCS-FM1 Mapper

사용자가 원하는 DCS-BIOS 기능을 자유롭게 FM-1 버튼과 노브에 할당하고, 실제 항공기 상태를 모니터링한다.

## C. Shared Protocol

Firmware와 Mapper가 안정적으로 입력 이벤트와 화면 데이터를 교환한다.

## D. 백업/복구 도구

순정 펌웨어 백업과 Flash 복구를 전담한다. 펌웨어 앱은 이 도구 없이도 동작하며, Flash 쓰기는 이 도구에서만 수행한다.

**최종 목표:** 기존 실물 UFC/DDI를 유지하면서, FM-1 여러 대를 F/A-18C의 ELEC, ECS, INTR LT, SENSOR 및 기타 시스템 패널로 자유롭게 구성하고, DCS-BIOS 양방향 통신을 통해 실제 항공기 상태와 동기화하는 확장형 컨트롤 시스템을 완성한다.

3. FM-1의 화면/입력/USB/오디오 제약(백라이트 공유, TE 없음)

장치 프로토콜은 USB-MIDI SysEx 바이너리로 구현하고 JSON을 장치에 보내지 마라.
DCS 펌웨어는 Flash에 쓰지 않는다. Flash 쓰기/삭제는 백업/복구 도구 범위이며,
장치별 백업과 복구 리허설이 검증되기 전에는 수행하지 마라.
두 FM-1은 서로 다른 하드웨어/Flash 리비전일 수 있으므로 HELLO의 flash_uid로 독립 식별하라.

## 17.2 플래시 칩 이슈의 구체적 의미

현재 커뮤니티 자료는 구형 Puya P25Q80H 계열의 JEDEC ID `0x856014`와 신형 UCUN UC25HQ80의 JEDEC ID `0xB36014`를 보고한다.

문제는 단순히 ID가 달라지는 것만이 아니다. 기존 펌웨어가 플래시 ID를 검사하는 위치가 여러 곳일 수 있다.

- 기존(순정) 앱 부팅 시 프로젝트/설정 저장 기능 활성화
- 업데이트 로더의 지원 칩 검사
- 복구 메뉴/복구 진입부
- 플래시 읽기/쓰기 도구
- 저장 데이터 영역 접근 코드

따라서 앱 코드의 ID 비교문 한 곳만 수정하는 것은 불충분하다. UCUN 칩에서 일부 펌웨어가 실행은 되더라도 저장이 RAM에만 남거나 다음 업데이트가 차단되는 사례가 보고되어 있다.

공개 SLOOP UC25HQ80 패치는 저장 경로, 업데이트 로더의 known-chip 검사, recovery entry의 세 지점을 수정했다고 설명한다. 이 자료는 수정 지점을 파악하는 참고 사례이며, 해당 패치가 DCS 펌웨어에 그대로 적용 가능하다는 뜻은 아니다.

필수 구현 원칙 (백업/복구 도구 범위):

1. Flash ID 검사 지점을 소스 전체에서 검색한다.
2. 애플리케이션/부트로더/업데이트/복구 코드의 검사 결과를 일관되게 관리한다.
3. 각 장치의 실제 ID를 읽어 로그에 남긴다.
4. 알려진 두 ID 외에는 쓰기·삭제를 금지한다.
5. 저장 후 전원 완전 차단 및 재부팅으로 영속성을 확인한다.
6. 두 장치가 서로 다른 ID여도 Mapper와 펌웨어 앱이 독립적으로 정상 작동해야 한다(앱은 Flash를 쓰지 않음).

## 17.3 부트로더/복구 관련 공개 자료에서 확인된 사항

m-bootloader 저장소 README는 다음 기능을 설명한다.

- FM-1에서 REC 키 조합으로 ROM USB download mode 진입
- PLAY 키 조합으로 복구 메뉴 진입
- USB MIDI 기반 펌웨어 재설치 및 플래시 읽기/백업
- 플래시 상태/칩 ID/펌웨어 상태를 표시하는 복구 메뉴
- 별도 M-Flasher flash loader
- 패키지 형식, 로더 프로토콜, 부팅 및 메뉴의 시뮬레이션 테스트
- ASan/UBSan 및 reproducible build 테스트 명령

위 내용은 해당 오픈소스 부트로더가 구현/설명하는 기능이다. 제조사 공식 펌웨어의 키 조합과 동일하다고 단정하지 않는다. 실제 장치에서 키 조합을 시험하기 전에 해당 프로젝트 문서의 정확한 보드/부트로더 조건을 확인한다.

## 17.4 하드웨어 자료에서 확인된 사양 및 미확인 영역

커뮤니티 개발 위키의 Hardware Overview는 다음을 기록한다.

- JieLi AC791N / WL82 계열
- pi32v2, `r3` CPU target
- 듀얼 코어 및 SRAM (앱 슬롯 581KB, RAM 96KB + 풀 336KB로 측정)
- 1MiB SPI NOR
- 240×240 컬러 TFT, ST7789 계열, RGB565, SPI1
- TE 신호선 없음, 백라이트 PA2가 키 매트릭스 인에이블과 공유
- 27 note keys, 14 buttons, 7 quadrature encoders, MASTER ADC
- USB-MIDI 및 ROM download mode (순정 펌웨어 USB ID `4C4A:C755` 보고)
- 오디오 출력 경로와 제어선

추가 확인 사항:

- 기기 순정 펌웨어는 2026-10 기준 V16이 배포 중이며, FM1 Open 소스는 V14 기준이다.
- fm1-base의 무선 없는 템플릿은 flash 77KB, RAM 27KB, 풀 68KB로 측정되었다.
- Flash UID는 백업/플래시 도구 경로에서 읽을 수 있다고 보고되어, 장치 세션 식별자로 사용할 수 있다.

다만 해당 위키 자체가 비공식이며 일부 항목은 실측/역공학/SDK 추정이 혼합되어 있다. 정확한 보드 리비전, 플래시 패키징(SiP/외장 부품 여부), 화면 컨트롤러 세부 모델, 입력 매트릭스 배선은 실제 두 장치에서 확인한다.

## 17.5 DCS-BIOS 공개 프로토콜 조사

DCS-BIOS 공식 Developer Guide는 다음을 설명한다.

- 명령 입력: 줄바꿈 종료 plain-text 명령을 UDP 7778로 전송
- 상태 출력: 바이너리 export stream을 UDP multicast `239.255.50.10:5010`으로 수신
- Windows에서 동일 스트림을 여러 프로그램이 수신하려면 UDP 소켓의 `allowreuseaddr` 설정이 필요
- 멀티캐스트 대신 `BIOSConfig.lua`를 통한 unicast 복사도 가능
- TCP 7778도 가능하지만 DCS 내부에서 blocking 부담이 생길 수 있어 UDP 권장
- `Saved Games/.../Scripts/DCS-BIOS/doc/control-reference.html`에서 지원 모듈과 컨트롤 정의를 확인할 수 있음

Mapper는 기존 UFC/DDI와 같은 DCS-BIOS export 스트림을 함께 수신할 수 있도록 소켓 옵션을 적용한다. 기존 `Export.lua` 및 DCS-BIOS 설정을 무단으로 교체하지 않는다.

## 17.6 라이선스 검토 기준

- FM1 Open의 앱 소스, SDK, 바이너리 엔진, 툴체인 및 서드파티 코드는 라이선스가 서로 다를 수 있다. 저장소 최상위 LICENSE만 보고 전체 파일을 동일 라이선스로 취급하지 않는다.
- m-bootloader는 저장소에 MIT 라이선스를 표시하지만, 함께 사용하는 플래셔/툴/서드파티 코드는 별도 확인한다.
- 커뮤니티 BSP/HAL 코드를 가져올 때 파일 단위 저작권 및 라이선스를 확인한다.
- GPL 코드가 DCS-FM1 펌웨어에 포함되는 경우 소스 공개/배포 의무와 바이너리 배포 방식을 검토한다.
- 사용자가 개인적으로 사용하는 것과 공개 배포/상업 배포는 법적 요구사항이 다르다. 배포 전 라이선스 인벤토리와 NOTICE를 작성한다.
- 순정 펌웨어 이미지, 음원 엔진, 프리셋/샘플 데이터는 소스코드 라이선스와 별도 권리일 수 있으므로 저장소에 임의로 포함하거나 배포하지 않는다.
- 기준 베이스인 fm1-base/felucca-bsp는 MPL-2.0이며, 그 위에 작성한 앱 코드는 임의 라이선스를 사용할 수 있다. 수정한 MPL 파일은 배포 시 공개 의무가 있다.
- DCS 펌웨어는 JieLi Bluetooth/WiFi 라이브러리를 링크하지 않으므로, 해당 라이브러리 사용에 따른 재링크 예외나 라이선스 전환을 요구하지 않는다.

# 18. 장비 미보유 단계 개발 실행 계획

## 18.1 개발 원칙

현재 사용자의 FM-1 실물 장비를 사용할 수 없는 상태이므로 개발을 멈추지 않는다. PC 측 소프트웨어와 하드웨어 독립 로직을 먼저 완성한다. 단, 실제 하드웨어에서 검증되지 않은 항목은 완료로 표시하지 않는다.

## 18.2 PC 시뮬레이터 구성

### A. Virtual FM-1 Device

- 장치 ID 및 별칭 (`flash_uid` 기반 세션)
- USB 포트/가상 MIDI 포트 식별자 (동일 이름 2대 포함)
- 펌웨어 버전/프로토콜 버전
- Flash ID 선택: `0x856014`, `0xB36014`, `UNKNOWN`
- 입력 이벤트 재생: 버튼 pressed/released, encoder CW/CCW, potentiometer
- Display Update 수신 및 화면 버퍼 출력
- 연결/분리/지연/패킷 오류/스왑 시뮬레이션

### B. Virtual Flash (백업/복구 도구 테스트용)

- 1MiB 가상 메모리 이미지
- Puya 및 UCUN ID 프로파일
- JEDEC ID 읽기 응답
- READ/PROGRAM/ERASE 명령 모델
- 범위 초과/정렬 오류/쓰기 보호/unknown ID 시나리오
- 전원 차단 시뮬레이션
- 기록 전후 SHA-256/CRC 비교
- 두 개의 가상 장치가 각각 다른 Flash ID를 갖는 혼합 리비전 테스트

주의: Virtual Flash는 백업/복구 도구의 논리 및 오류 처리 검증 도구다. 실제 칩의 전기적 특성, 타이밍, 제조사별 미세 차이 및 실제 부팅을 검증하지 않는다. DCS 펌웨어 앱은 이 가상 Flash를 사용하지 않는다.

### C. DCS-BIOS Simulator

- 컨트롤 카탈로그 샘플 파일 로드(JSON 부재/폴백 시나리오 포함)
- 명령 수신/파싱
- 상태 export 패킷 생성/전송
- 상태값 변경 이벤트 생성
- 동기화/부분 패킷/패킷 유실/재연결 테스트

실제 DCS-BIOS 설치 경로를 읽는 통합 모드는 별도로 유지한다. 샘플 데이터는 실제 F/A-18C 컨트롤 정의와 혼동되지 않도록 `SIMULATED`로 표시한다.

### D. fm1-base 호스트 시뮬레이터 / 브라우저 에뮬레이터 (1차 펌웨어 검증)

- 동일한 앱 코드를 PC와 브라우저에서 실행해 화면·패널·USB-MIDI 경로를 검증
- 실기 없이 P3 게이트를 통과하기 위한 기본 환경
- 실기 고유 동작(백라이트, 오디오 잡음, 플래시, USB 열거)은 검증 대상이 아님

## 18.3 실물 장치 확보 전 완료 가능한 산출물

- Mapper의 장치 목록/별칭/프로파일 UI
- DCS-BIOS 카탈로그 로더 및 검색(폴백 포함)
- DCS-BIOS UDP 송신/수신 및 export decoder
- 매핑 엔진과 버튼/엔코더 동작
- Firmware–Mapper 프로토콜의 PC 테스트 도구
- fm1-base 기반 펌웨어 앱(에뮬레이터에서 화면/입력 검증)
- Virtual FM-1 / Virtual Flash / DCS-BIOS Simulator
- 테스트 케이스 및 자동화 단위 테스트
- fm1-base/felucca-bsp 빌드 환경 구성

## 18.4 실물 장치가 있어야 완료 가능한 산출물

- 두 장치 각각의 Flash ID/UID/하드웨어 리비전 확정
- 실제 펌웨어 부팅 및 화면 출력
- 버튼/엔코더/MASTER 노브 전체 입력 확인
- 실제 USB MIDI/전용 USB 통신 안정성
- 실제 Flash 저장 영속성 (백업/복구 도구)
- 실제 펌웨어 업데이트/복구
- 두 장치 혼합 리비전 동시 연결 및 장시간 안정성
- DCS 실행 중 실제 F/A-18C 조작과 화면 상태 동기화

## 18.5 통합 테스트 조합

백업/복구 도구의 가상 Flash 하네스(§18.2 B)에서 수행하는 조합이다. 펌웨어 앱은 Flash를 쓰지 않으므로 "쓰기/검증"은 모두 도구 범위다.

| 테스트 ID | 가상 장치 A | 가상 장치 B | 예상 결과 |
| --- | --- | --- | --- |
| SIM-FLASH-01 | Puya `0x856014` | Puya `0x856014` | 양쪽 독립 인식, 도구에서 독립 쓰기/검증 |
| SIM-FLASH-02 | Puya `0x856014` | UCUN `0xB36014` | 서로 다른 드라이버 프로파일로 동시 동작 |
| SIM-FLASH-03 | UCUN `0xB36014` | Puya `0x856014` | 장치 연결 순서와 무관하게 동시 동작 |
| SIM-FLASH-04 | UCUN `0xB36014` | UCUN `0xB36014` | 양쪽 독립 인식, 도구에서 독립 쓰기/검증 |
| SIM-FLASH-05 | Puya | UNKNOWN | unknown 장치의 쓰기 차단, Puya 장치는 정상 |
| SIM-FLASH-06 | UCUN | UNKNOWN | unknown 장치의 쓰기 차단, UCUN 장치는 정상 |

두 장치가 같은 종류의 Flash를 사용하는 경우에도 장치별 세션/프로파일은 별도로 유지한다. Flash ID는 장치의 유일 식별자가 아니므로 동일 ID만으로 장치를 구분하지 않는다.
